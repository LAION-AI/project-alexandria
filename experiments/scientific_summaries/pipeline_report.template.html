1. What this pipeline does

The pipeline asks a language model to turn the available text of a scientific paper into a structured summary. Most summary statements are paired with a short quotation from the paper. Software checks the structure and the existence of those quotations; the model is called again only when corrections are needed. A separate, fixed model then answers paper-specific questions using the summary, measuring how much useful knowledge survives compression.

They are planning extrapolations, not measurements on JUPITER. The requested local 9B runs use Q8_0/llama.cpp; no completed 9B summary score is claimed here.
  1. Freeze the inputs Save the dataset paper texts, existing summaries, document IDs, questions, and content hashes.
  2. Generate independently Send one whole paper per request. Batch requests from different papers; do not expose questions or answers to the generator.
  3. Check structure and source spans Reject invalid JSON, missing fields, unfinished responses, or quotations absent from the frozen text.
  4. Repair only failed parts Request field-local patches; if needed, select real source fragments or drop unsupported entries. Revalidate every edit.
  5. Evaluate retained knowledge Give the fixed Qwen2.5-7B student the summary narrative and the same multiple-choice questions used for all controls.
  6. Audit and publish artifacts Check source, prompt, question, and evidence consistency; preserve raw outputs, failures, seeds, and uncertainty intervals.

Terminology: a token is a unit of model text, not necessarily a word. Prefill reads the input; decode generates the output. One GPU-hour is one GPU allocated for one hour; 1,024 GPUs running for one hour consume 1,024 GPU-hours.

2. Data, questions, and information isolation

The source is laion/Scientific-Summaries. The frozen convenience sample contains 100 records: 50 from the arXiv configuration and 50 from Bethgelab. Selection used deterministic offset pools and a length filter, preferring body-text records over abstract-only entries. The main selection path requires 8,000–30,000 characters, at least 1,500 words, an existing summary of at least 2,000 characters, a title and key-results field, no reported retraction, and no duplicate text hash; its marker preference is not identical to the fallback selection path.

The user approved proceeding with the 97 papers with ready QA and preceding KU/control results. The excluded IDs are @@EXCLUDED@@. They were not excluded according to student scores. The dataset manifest records observed revision 232547b7b938a6588ce5d9d7faa96384860b7a16, but the original viewer API calls were not revision-pinned. Therefore, reproduction must use the saved files and their hashes, not assume a fresh download will return identical rows.

“Paper text” does not guarantee a complete publisher PDF. These are the available dataset texts. Missing bibliographies or other sections were not independently restored. A conclusion marker and a length threshold do not prove completeness. The experiment measures retention of the supplied text, not of unseen sections.

Luna agents authored ten difficult, four-choice questions per ready paper using only its saved source text. Each question includes a correct answer, plausible distractors, rationale, and a source passage. The question validator checks schema and literal evidence alignment, not independent semantic correctness of every gold answer. The saved authoring protocol is in Appendix A9; frozen questions are the exact reproduction input.

  • Generator and repair calls: source text, summary instructions, and—when repairing—failed fields/errors or source-candidate tasks. Never questions, gold answers, existing summaries, KUs, or student scores.
  • Student calls: one context condition plus a question and options. Never gold answers, evidence passages, or rationales.
  • Offline scoring: compare the parsed student choice with the frozen gold label. Deterministically balance answer positions and shuffle distractors with seed 250219413.

Saved inputs: papers and dataset summaries, dataset manifest, authored QA, and comparison cohort. The dataset declares CC-BY-4.0; retain its attribution and source identifiers. This report is not a blanket legal assessment of all original publisher material.

3. Whole-paper generation and batching

This is not the chunked KU pipeline. A summary request contains the entire frozen paper text. Papers run independently in parallel; corrections within an individual paper depend on its previous draft. The queue processes models in order—27B generation, fixed-student evaluation, Ornith generation/evaluation, then Qwen3.5-9B generation/evaluation—not all models simultaneously.

@@MODELS@@

The measured workstation has two 24-GB RTX 3090s. The 27B model spans both GPUs (tensor parallelism 2), with eight concurrent requests continuously batched by vLLM. Each local 9B GGUF uses one GPU and four llama.cpp slots, with Q8_0 weights and Q8_0 K/V cache. A total context allocation of 131,072 tokens is divided across four slots, yielding 32,768 tokens per request.

Common generation settings: temperature 0.2; top-p 0.95; thinking disabled; maximum 16,000 output tokens; 32,768-token input-plus-output context limit. The maximum is a budget, not the observed output length. Initial seeds are int(SHA256(document_id)[:8], 16) % 2147483000, incremented with attempt number. The secondary stage starts at that seed plus 100. The GGUF client explicitly sets top-k 0, min-p 0, and repeat penalty 1.

Before each request the serving tokenizer counts the chat input. If the input plus requested output budget exceeds the context limit, the request is rejected; the source is never silently truncated. This protects comparability but means longer papers need a separately specified larger-context protocol.

JSON-object constrained decoding is requested. For vLLM the payload uses {"type":"json_object"}. The installed llama.cpp transport additionally needs the nonempty schema {"type":"json_object","schema":{"type":"object"}}; an empty schema had disabled its constraint. This is a JSON syntax constraint, not a guarantee of the 19-field schema or scientific accuracy. The transport fix and explicit zero-based candidate indices are disclosed in the repository.

4. What the source checks actually establish

Validation is primarily deterministic software, not another GPU model. It checks complete parseable JSON, duplicate keys, the prescribed field structure and types, grounded-entry shapes, citation shapes, and a nonempty usable executive summary. Root field order can be restored and logged before final validation. An enclosing Markdown fence can be removed and logged, but arbitrary prose is not searched for a partial JSON fragment. A response ending because its output budget was exhausted is rejected.

For every retained proof quote, the validator requires nonempty text of at most five whitespace-delimited words and locates it in the frozen source. Exact matching is tried first, followed by whitespace alignment and Unicode NFKC/ligature alignment. The stored ledger contains the actual source substring, character offsets, field path, original quote, and alignment flag. No approximate semantic match or invented replacement is accepted. Bibliographic citation keys must also be locatable in the source.

Existence is not entailment. A quotation can be present while supporting a different method, population, direction of effect, or number than the attached statement. Five-word fragments often omit the context needed to establish a claim. Passing this check does not prove scientific factuality, completeness, faithful interpretation, correct citation influence, or correctness of every metadata field.

In particular, the executive-summary text and claim descriptions are not exhaustively checked sentence by sentence for semantic support. The validator does not comprehensively detect every template placeholder or unsupported ethics claim by meaning; the prompts instruct the model not to retain these, and nonexistent citation/quote strings fail the literal checks. The distinction between an instruction and an enforced check matters.

Implementation: validate_summary and narrative_context, evidence_span, and independent field validation. The appendix preserves the exact prompts rather than describing them as a stronger verifier than they are.

5. Bounded corrections, recovery, and failure handling

Repair versions are not interchangeable. The measured, completed 27B run uses V2 (described in the next two subsections). Restarted 9B runs use V3 after their V2 smoke tests failed. Their initial system prompt, source texts, and final validator remain unchanged, but the repair policy and additional repair user messages differ. This must be disclosed when comparing results or extrapolating repair costs.

Stage 1 — generate, then patch only invalid fields

The queue explicitly allows six calls in the primary stage, including initial generation. If a complete draft exists, all 19 fields are validated independently. The same generator receives the original source, only the invalid fields, and the detected errors. It must return exactly those requested top-level fields. Untargeted fields cannot change. Repair outputs are capped at 4,096 tokens; supported statements should be preserved, unsupported entries removed, and absent fields left empty. If there is no parseable complete draft, a format reminder is appended and initial generation is retried.

Stage 2 — choose real source anchors or drop entries

Persistent quote errors can trigger up to six additional calls. Software proposes up to 16 literal 3–5-word fragments for an invalid entry using lexical overlap with its narrative and erroneous quote, weighted toward rare terms. This retrieval is only a candidate proposal mechanism. Each call handles at most eight entries and includes the whole source. The same model selects a zero-based candidate index only if it supports the statement, including its numbers and negations, or returns "drop" if none does.

All choices are checked before any edit is applied. Selecting a candidate replaces the quotation with that real source span while retaining the narrative; choosing “drop” removes the entry. Candidates, choices, offsets, and removals are saved. Remaining schema/citation errors use field-only patches. The final edit is always revalidated. This model-based selection examines support for the repair tasks, not all statements in all summaries, and it can still make semantic mistakes.

V3 — restarted 9B repair policy

The failures exposed a mismatch between the requested single-entry objects and conventional {narrative,evidence} objects, output-budget exhaustion when many fields were rewritten together, and more invalid quotes than six batches could handle. V3 losslessly rewraps only unambiguous alias pairs; narrative and quote strings are unchanged, and each transformation is logged. For old repair protocols it prefers the original detailed generation over a shortened repair draft. For already repaired V3 drafts it preserves the repaired narrative, source selections and audit history and revalidates all fields. Initial generation has at most two independently seeded attempts.

Malformed fields are patched individually with an explicit shape-only example (at most two calls per field, 4,096 output tokens each). Quote-only problems are then processed in batches of eight. The call limit is twice the required initial quote-batch count plus two, bounded below by four and above by 64. Each provided candidate includes a short surrounding source context. All index selections are checked atomically, unsupported drops are recorded, and the original final literal-source validator is mandatory. This avoids treating format alignment as evidence validation. The new templates and field examples are in Appendix A13–A15 and in each V3 run snapshot; an implementation hash prevents silently changing a resumed checkpoint.

The citation shape example is an empty string for an absent bibliography, avoiding a fictitious citation key that the model could copy. Actual bibliography citations remain allowed and subject to the same validation. After a diagnosed implementation change, explicit --recover-failed-cache recovery permits only a failed-only V3 checkpoint with unchanged model/weights, source, prompts and generation settings. It records the prior checkpoint and implementation hashes; historical saved elapsed time is included. This is an auditable repair continuation, not a new independent generation experiment.

Complete draft → independent field checks
  ├─ all pass → final evidence ledger → save summary
  └─ failures → field-only patch → recheck
       └─ persistent quote failures → propose actual source fragments
            ├─ supporting candidate chosen → retain statement + real quote
            └─ "drop" → remove entry
       └─ still invalid after bounded attempts → save failure; stop before scoring

Operational robustness

Requests retry transient transport/server errors up to three times with backoff; nontransient summary HTTP errors are not blindly repeated. Atomic checkpoints are saved after completed documents. A resumed run verifies source and configuration hashes and skips valid completed documents. A failed cohort pass may be retried once for missing papers, so actual journals can exceed a single six-call limit. Persistent failures remain visible and stop the queue instead of silently changing the evaluation denominator.

The detached launcher survives a terminal closing. Queue and publisher locks prevent duplicate invocations; locks are not deleted while running. The runner waits for free GPUs and only stops its own isolated server process groups. Explicit server adoption verifies process identity. These safeguards do not imply that interrupted, uncheckpointed work is recoverable or that all hardware/server failures disappear.

Why retain the checks? Cheap deterministic checks and traceable evidence prevent unusable outputs and make errors inspectable. The expensive repair loops are a separate policy choice. At large scale, compare bounded repair against one-pass generation with the same QA and semantic spot checks, reporting removals, lost coverage, failure rate, and cost. Do not silently change the protocol and present it as the same experiment.

6. Evaluation with the unchanged fixed student

The “judge” here is a question-answering student, Qwen/Qwen2.5-7B-Instruct. It is not an independent claim-by-claim factuality judge. For each question it sees no context, the frozen source, the existing dataset summary, the preceding KU representation, or the newly generated summary. The newly generated context concatenates substantive narrative fields, including claims and takeaways, but excludes metadata, proof quotes, and citation rankings.

The exact historical system and user prompts are preserved in Appendix A10–A12, including their unusual wording. The historical ASCII sanitizer is applied after substituting the context and question; it can remove scientific Unicode and punctuation. The parser splits the response on semicolons and accepts the first stripped field exactly equal to A, B, C, or D, without case conversion. Up to five total formatting attempts use the same prompt. Final invalid answers count as wrong.

Student settings: BF16; tensor parallelism 1; vLLM 0.27.1; temperature 0.5; top-p 0.95; maximum 100 output tokens; frequency and presence penalties 1.05; four concurrent requests; 32,768-token current context cap. Input tokens plus the 100-token output allowance are preflighted. Student requests have no explicit random seed, so exact rerun predictions are not guaranteed. Previously frozen controls are reused only when the questions/options/gold and effective prompt hashes match.

Completed 27B result: raw scores and student responses. The intervals resample documents—not individual questions—10,000 times with seed 250219413, keeping each paper’s ten questions together. These are sampling-uncertainty intervals, not guarantees about rerun variance or all scientific literature.

7. GPU-hour planning for 60 million papers

JUPITER’s standard accelerated node contains four GH200 superchips; each GPU has 96 GB HBM3 with 4 TB/s bandwidth. These specifications must not be confused with the larger-memory H200 used in some published benchmarks. JSC hardware documentation

Measured workload, not guessed summary lengths

@@WORKLOAD@@

The initial output count includes structured JSON and proof quotes, not only the free narrative. The validated-workload estimate includes all distinct saved calls across successful and failed journals. Copied historical attempts are deduplicated by document, phase, seed, prompt hashes, response hash, and recorded duration. It does not recover calls lost before checkpointing. The successful-journal mean is about 4.5 calls per paper; the saved-call aggregate is slightly larger.

The local GPU-hour number is a checkpointed active-time proxy: two allocated GPUs times saved generation/repair wall time. It excludes startup, idle gaps, and possibly uncheckpointed interrupted intervals. It is not a scheduler billing total and is not converted to GH200 hours using an unsupported hardware multiplier.

Research anchors and explicit assumptions

A self-reported operator result for Qwen3.8-27B on one H200 reports about 1,394 aggregate output tokens/s using SGLang and MTP speculative decoding. It is not a matched vLLM/GH200 scientific-summary measurement. Operator benchmark. A separate Qwen3.8 FP8 H200 capture workload reports 4.4 prompts/s at roughly 4,000 tokens per conversation; this is prefill/hidden-state capture, not autoregressive summary generation. SpecForge measurement

For Qwen3.5-9B, GPUStack reports about 5,200 aggregate output tokens/s on an H100 in its short-context ShareGPT profile. Its long-context and generation-heavy profiles use different request patterns; total tokens/s must not be mistaken for output tokens/s. These measurements do not establish FP8/GH200 performance at our approximately 8,165-input/3,059-output workload. GPUStack benchmark and settings

No directly matched benchmark was found. The rates below are our planning assumptions informed by these reference measurements, not published GH200 results or demonstrated optimal settings. The range varies throughput and utilization; it is not a statistical confidence interval.
@@RATES@@ 
GPU_hours = N / 3600 × (I / P + O / D) / η

N = number of papers
I, O = mean input/output tokens per paper, summed over all included calls
P, D = phase-specific aggregate prefill/decode tokens per second per GPU
η = effective utilization, including ordinary operational losses

Important: P and D are phase capacities. Do not substitute an already
end-to-end measured decode rate and then count its prefill cost again.

Fast/central/slow assumptions are explicit in the machine-readable companion. For 27B they use P = 16,000/10,000/6,000, D = 1,500/900/700, η = 0.90/0.85/0.80. For 9B they use P = 40,000/25,000/15,000, D = 4,000/2,500/1,500 with the same utilization values. The model approximates additive phase costs; scheduling, cache reuse, batching, and longer-context attention can change actual cost.

@@COSTS@@

Rounded central headlines are 80,000 GPU-h for one-pass 27B and 200,000 GPU-h with its observed repairs; 30,000 GPU-h for one-pass 9B and 75,000 GPU-h with the same assumed repair burden. The 9B validated estimate borrows the 27B call/token distribution; its actual repair rate and output length are not yet measured here. Smaller-model speed does not guarantee equal scientific coverage or QA performance.

@@WALL@@

Wall times divide central GPU-hours by GPU count, assuming near-linear independent-paper scaling and adequate data supply. They exclude queue waiting. Costs exclude PDF parsing/OCR, QA authorship, fixed-student evaluation, and archival storage. The cohort averages about 3,500 source words; a 60-million-paper corpus with longer full texts, larger outputs, or thinking enabled needs a new workload estimate. FP8 may also change output quality and repair rates relative to the measured mixed-INT4 run.

Proposed GH200 deployment—not an implemented JUPITER benchmark

Start with one FP8 replica per GPU (four per node), continuous batching, length buckets, chunked prefill, and GPU-resident caches. Tune concurrent requests and batched-token limits; retain CUDA graphs where supported. Benchmark FP8 KV cache for both throughput and quality rather than assuming it automatically doubles speed. MTP is optional and no speculative-decoding gain is included in the central estimates. These are deployment hypotheses to test, not a claim of a global optimum. 27B vLLM recipe, 9B vLLM recipe, FP8 KV-cache documentation

Use Qwen/Qwen3.8-27B-FP8 or RedHatAI/Qwen3.5-9B-FP8-dynamic, not GGUF files, for this proposed native vLLM FP8 deployment. Pin new model revisions, tokenizer hashes, container digest, ARM64/CUDA build, and cache configuration. The workstation queue is not a ready-made Slurm/JUPITER launcher: a distributed shard scheduler and restart-safe aggregation must be separately implemented and verified.

Before allocating the full job: benchmark 1,000 representative papers on one four-GH200 node, including warmup, real repairs, failure rates, and token-length tails. Allow roughly 1–2 hours for the pilot and tuning, then replace assumptions with measured end-to-end papers/GPU-hour. For large-scale planning, also benchmark storage and data-loader throughput and semantic quality.

9. What conclusions are justified?

Supported: on this fixed 97-paper/970-question convenience cohort, the completed grounded-summary pipeline makes substantially more paper-specific questions answerable than no context, while the full supplied source performs better. The output can be inspected against saved source spans, and every recorded correction can be audited.

Not established: universal summary factuality; complete publisher-PDF coverage; correctness of every authored gold answer; the importance of all omitted knowledge; identical quality for FP8 versus mixed-INT4; equal repair rates for 9B; or the actual optimal throughput of this workload on JUPITER. GPU-hour planning ranges are not scientific confidence intervals. Stochastic generation, runtime versions, and batching can change outputs even with some fixed seeds.

Recommended scale-up gate: retain cheap deterministic validation, benchmark the cost and benefit of repair policies, review random and high-risk samples against full source passages, and report factual support and knowledge coverage separately. A semantic verifier would be an additional experiment—not a feature already guaranteed by the current quote-existence checks.
